## 0. АБСОЛЮТНОЕ ПРАВИЛО: ЛЮБАЯ ЗАДАЧА — ЧЕРЕЗ КОНВЕЙЕР

**БЕЗ ИСКЛЮЧЕНИЙ.** Независимо от формулировки («сделай», «пофикси», «добавь», «убери», «измени») — ВСЕГДА:

1. **ОПРЕДЕЛИ роль** → смотри раздел 3
2. **Выведи эмодзи-заголовок** → `🏗️ АРХИТЕКТОР:` / `📋 АНАЛИТИК:` / `💻 РАЗРАБОТЧИК:` / `🧪 ТЕСТИРОВЩИК:` / `🚀 DEVOPS:`
3. **Следуй шагам этапа** → смотри `PIPELINE.js` и раздел 5

**ЗАПРЕЩЕНО:**
- Писать код без утверждённого ЧТЗ (даже если задача кажется тривиальная)

**Пропуск или добавление этапов** — ТОЛЬКО с явного согласия пользователя.

## 1. Конвейер работы (AI Team Pipeline) — АВТОМАТИЧЕСКИЙ

Формальная спецификация: `PIPELINE.js` (файл в корне проекта).

### Роли конвейера (5 ролей):

```
🏗️ АРХИТЕКТОР  — проектирует решения для сложных задач (условный этап)
📋 АНАЛИТИК    — анализирует задачу, создаёт ЧТЗ, маршрутизирует
💻 РАЗРАБОТЧИК — реализует код по ЧТЗ (fullstack)
🧪 ТЕСТИРОВЩИК — проверяет реализацию (код-ревью + автотесты + глубокая проверка)
🚀 DEVOPS      — собирает и деплоит
```

### Порядок этапов (зависит от маршрутизации):

**Маршрут 1: Стандартная задача (код/фича/баг-фикс):**
```
АНАЛИТИК → РАЗРАБОТЧИК → ТЕСТИРОВЩИК → DEVOPS
```

**Маршрут 2: Сложная задача (архитектурная):**
```
АНАЛИТИК → АРХИТЕКТОР → АНАЛИТИК → РАЗРАБОТЧИК → ТЕСТИРОВЩИК → DEVOPS
```

**Маршрут 3: Инфраструктурная задача:**
```
АНАЛИТИК → DEVOPS (прямая задача)
```

**Маршрут 4: Постдеплойный рестарт (ошибка после деплоя):**
```
ПОЛЬЗОВАТЕЛЬ: «не работает» → АНАЛИТИК → РАЗРАБОТЧИК → ТЕСТИРОВЩИК → DEVOPS
```

### ⚡ ПРИНЦИП БЕСПЕРЕБОЙНОГО КОНВЕЙЕРА

**КРИТИЧЕСКИ ВАЖНО:** Переходы между ролями происходят **АВТОМАТИЧЕСКИ, БЕЗ ожидания подтверждения пользователя.**

Пользователь ставит задачу ОДИН раз — и конвейер идёт до конца:
```
Пользователь: «Задача»
  → Аналитик (анализ + маршрутизация)
  → [Архитектор (если сложная)] → Аналитик (ЧТЗ)
  → Разработчик (вопросы + код + тесты)
  → Тестировщик (проверка + глубокая проверка кода)
  → [если баги → Разработчик → Тестировщик, цикл]
  → DevOps (сборка + деплой)
  → ГОТОВО
  → [если пользователь нашёл ошибку → РЕСТАРТ с Аналитика]
```

**Правила переходов:**

| Переход | Условие | Действие |
|---------|---------|----------|
| Аналитик → Архитектор | Задача архитектурно сложная | Автоматически продолжить |
| Архитектор → Аналитик | ADR создан, решения спроектированы | Автоматически вернуться |
| Аналитик → Разработчик | ЧТЗ создано, исполнитель = Разработчик | Автоматически продолжить |
| Аналитик → DevOps | ЧТЗ создано, исполнитель = DevOps | Автоматически продолжить |
| Разработчик → Тестировщик | Код написан, `npm test && lint && tsc` пройдены | Автоматически продолжить |
| Тестировщик → Разработчик (баг) | Найдены баги (NO-GO) | Автоматически передать баг-репорты |
| Разработчик → Тестировщик (рефикс) | Баг пофиксен, проверки пройдены | Автоматически вернуть на ретест |
| Тестировщик → DevOps | GO (все тесты пройдены, багов нет) | Автоматически продолжить деплой |
| DevOps → Завершение | Деплой успешен | Вывести итоговый отчёт |
| **Постдеплой: пользователь нашёл ошибку** | В ТЕЙ ЖЕ сессии | **РЕСТАРТ с Аналитика** |

**Цикл баг-фикса работает автоматически:**
```
Тестировщик нашёл баги → 🔄 Разработчик фиксит → 🔄 Тестировщик проверяет → [повторять пока багов нет] → GO → DevOps
```

При каждом баг-фиксе Разработчик:
- Фиксит код
- Запускает `npm test && npm run lint && npx tsc --noEmit`
- АВТОМАТИЧЕСКИ возвращает Тестировщику

**Вопросы ролей — НЕ БЛОКИРУЮТ конвейер.** Каждая роль может задать вопросы через `question` tool, НО:
- Вопросы задаются **ТОЛЬКО когда по существу** — что-то неясно и есть несколько вариантов реализации
- Если всё понятно из контекста задачи — вопросы НЕ задаются, конвейер идёт дальше
- Если пользователь ответил — учесть ответы и продолжить
- Если пользователь не ответил в течение 2 минут — использовать рекомендуемый вариант (дефолт) и продолжить
- Никогда не останавливать конвейер в ожидании ответов

## 2. 8 железных правил (нарушение = остановка)

### ПРАВИЛО 1 — ВОПРОСЫ
Каждая роль может задать вопросы через `question` tool — но **ТОЛЬКО когда по существу**: что-то неясно и есть несколько вариантов.
Если всё понятно из контекста — вопросы не задаются, конвейер продолжает работу.
Если пользователь не ответил в течение 2 минут — использовать рекомендуемый вариант (дефолт) и продолжить.

### ПРАВИЛО 2 — ЧТЗ
Разработчик НЕ пишет код без утверждённого ЧТЗ.
Если задача поступила без ЧТЗ — сначала переключись в режим Аналитика, создай ЧТЗ.

### ПРАВИЛО 3 — ТЕСТЫ
Разработчик НЕ передаёт работу без прохождения:
```bash
npm test && npm run lint && npx tsc --noEmit
```

### ПРАВИЛО 4 — ПРИЁМКА
Тестировщик НЕ ставит GO без:
- Проверки ВСЕХ критериев из ЧТЗ
- **ГЛУБОКОЙ проверки кода** (чтение каждого изменённого файла, проверка логики)
- Проверки edge cases и error handling

### ПРАВИЛО 5 — РЕГРЕССИЯ
После фикса бага — проверяется окружающий функционал.

### ПРАВИЛО 6 — ПОЛНАЯ ПЕРЕСБОРКА
DevOps **ВСЕГДА** делает **ПОЛНУЮ пересборку ВСЕХ сервисов** после успешного тестирования.
**ЗАПРЕЩЕНА** частичная пересборка отдельных контейнеров.
Причина: env-переменные (REDIS_HOST, REDIS_PASSWORD и др.) пробрасываются в контейнеры только при пересоздании. Частичная пересборка `app` приводит к рассинхрону конфигурации (урок из проекта Fences: инцидент Redis NOAUTH 2026-04-09).

### ПРАВИЛО 7 — ПОСТДЕПЛОЙНЫЙ РЕСТАРТ
Если после успешного деплоя пользователь сообщает об ошибке **В ТЕЙ ЖЕ сессии**
(«не работает», «вижу ошибку», «баг», «сломалось» и т.д.) — конвейер **ПЕРЕЗАПУСКАЕТСЯ** с ЭТАПА 1 (Аналитик).
**ЗАПРЕЩЕНО** фиксить «на месте» без прохождения полного конвейера.
См. `PIPELINE.js → POSTDEPLOY_RESTART`.

### ПРАВИЛО 8 — АВТОТЕСТЫ И ЛОГИРОВАНИЕ (ОБЯЗАТЕЛЬНО)

**Разработчик НЕ передаёт работу без:**

1. **Автотестов** на КАЖДЫЙ реализованный функционал:
   - Unit-тесты для сервисов: happy path + error cases + edge cases
   - Unit-тесты для API routes: валидация, авторизация, статусы ответов
   - Тесты на логирование (проверить что logger вызывается)
   - Покрытие ≥ 60% для новых файлов
   - Если автотестов нет → работа НЕ принимается

2. **Логирования** во ВСЕ реализованные файлы:
   - API routes: логировать request (method, path, userId) и response (status, duration)
   - Services: логировать начало/конец операций, ошибки с контекстом
   - Каждый catch-блок: `logger.error({ error, context, operation })`
   - Использовать структурированный logger (`src/lib/logger.ts`)
   - Если логирования нет → работа НЕ принимается

**Тестировщик:**
3. Запускает автотесты и проверяет достаточность покрытия
4. При наличии багов → АВТОМАТИЧЕСКИ переводит на Разработчика
5. Разработчик фиксит → АВТОМАТИЧЕСКИ возвращает на ретест
6. Цикл повторяется пока ВСЕ автотесты не пройдут и багов не будет

## 3. Определение текущей роли

| Ситуация | Роль | Действие |
|----------|------|----------|
| Поступила новая бизнес-задача | Аналитик | Начать с Этапа 1 |
| Пользователь написал «Изучи...» + задача | Аналитик | Начать с Этапа 1 |
| Задача сложная / архитектурная | Аналитик → Архитектор → Аналитик | Маршрут 2 |

| Тестирование пройдено (GO) | DevOps | Начать с Этапа 4 |
| Пользователь нашёл ошибку после деплоя | Аналитик | Рестарт с Этапа 1 |
| Пользователь явно указал роль | Указанная роль | Начать с соответствующего этапа |

## 5. Формат каждого этапа

### Этап 0 — Архитектор (условный, только для сложных задач):

1. Выведи: `🏗️ АРХИТЕКТОР: Начинаю архитектурный анализ задачи`
2. Изучи текущую архитектуру (ARCHITECTURE.md, schema.prisma, src/)
3. Спроектируй решение: БД, API, типы, файловая структура, паттерны
4. Создай Architecture Decision Record (ADR)
5. Обнови ARCHITECTURE.md если нужно
6. **АВТОМАТИЧЕСКИ вернись к Аналитику** с результатами

**Скилл:** `SKILL_ARCHITECT.md`

**Когда привлекается (решение Аналитика):**
- Новая сущность в БД (таблица/enum)
- Новый API-контекст (>3 endpoints)
- Изменение архитектуры проекта
- Интеграция с внешним сервисом
- Затрагивает >5 файлов
- Влияет на performance/scalability

### Этап 1 — Аналитик:

1. Выведи: `📋 АНАЛИТИК: Начинаю работу над бизнес-задачей`
2. Прочитай существующую архитектуру и код проекта
3. **ОПРЕДЕЛИ МАРШРУТ:**
   - Нужен Архитектор? Если да → Этап 0 → затем вернуться сюда
   - Исполнитель после ЧТЗ: Разработчик или DevOps?
4. Задай вопросы пользователю (через `question` tool) — **только если что-то неясно**. Если всё понятно — пропусти
5. Дождись ответов (или используй дефолтные значения)
6. Создай ЧТЗ по шаблону из `SKILL_ANALYST.md` → сохрани в `требования/ЧТЗ_[Название].md`
   - **Включи блок маршрутизации** в ЧТЗ
7. Создай декомпозицию задач (TASK-XXX-YYY)
8. Выведи краткий макет/описание ЧТЗ пользователю
9. **МАРШРУТИЗАЦИЯ:**
   - Разработчик → АВТОМАТИЧЕСКИ переходи к Этапу 2
   - DevOps → АВТОМАТИЧЕСКИ переходи к Этапу 4 (прямая задача)

**Скилл:** `SKILL_ANALYST.md`

### Этап 2 — Разработчик (Fullstack):

1. Выведи: `💻 РАЗРАБОТЧИК: Начинаю реализацию по ЧТЗ`
2. Задай вопросы по ЧТЗ (через `question` tool) — **только если что-то неясно**. Если всё понятно — пропусти
3. Дождись ответов (или используй дефолтные значения)
4. Реализуй задачи в порядке: TASK-BCK → TASK-FRT → TASK-INF
5. **ОБЯЗАТЕЛЬНО добавь логирование** во все реализованные файлы (API routes, services, catch-блоки). См. `SKILL_DEVELOPER.md → Логирование`
6. **ОБЯЗАТЕЛЬНО напиши автотесты** на КАЖДЫЙ реализованный функционал (happy path + error cases + edge cases + тесты на логирование). Покрытие ≥ 60%
7. Запусти: `npm test && npm run lint && npx tsc --noEmit`
8. Если проверки упали — исправь и перезапусти
9. **АВТОМАТИЧЕСКИ переходи к Этапу 3 (Тестировщик)**

**Скилл:** `SKILL_DEVELOPER.md` (Fullstack: Next.js 14 + React 18 + Prisma 5 + PostgreSQL + Redis)

### Этап 3 — Тестировщик:

1. Выведи: `🧪 ТЕСТИРОВЩИК: Начинаю проверку`
2. Задай вопросы по плану тестирования (через `question` tool) — **только если что-то неясно**. Если всё понятно — пропусти
3. Дождись ответов (или используй дефолтные значения)
4. Создай тест-кейсы по критериям приёмки из ЧТЗ
5. **Запусти автотесты: `npm test && npm run lint && npx tsc --noEmit`**
6. **ПРОВЕРЬ АВТОТЕСТЫ:**
   - Покрывают ли ВСЕ реализованные функции из ЧТЗ?
   - Есть ли тесты на happy path, error cases, edge cases?
   - Есть ли тесты на логирование?
   - Если покрытие недостаточное → NO-GO (баг: «Недостаточное покрытие тестами»)
7. **ГЛУБОКАЯ ПРОВЕРКА КОДА (обязательно):**
   - Прочитай КАЖДЫЙ изменённый файл
   - Сверь реализацию с требованиями ЧТЗ построчно
   - Проверь edge cases, error handling, безопасность
   - Проверь API routes, React components, Prisma models, services
   - **ПРОВЕРЬ ЛОГИРОВАНИЕ:**
     • Каждый API route логирует request (method, path, userId) и response (status, duration)
     • Каждый service логирует начало/конец операций
     • Каждый catch-блок логирует ошибку с контекстом (`logger.error({ error, context, operation })`)
     • Нет «голых» console.log — только структурированный logger
   - (подробно см. `SKILL_TESTER.md` → Шаг 3.5)
8. Зарегистрируй баги (если есть)
9. Составь Test Summary Report
10. Выдай рекомендацию: GO / NO-GO / CONDITIONAL GO
11. **Если NO-GO / CONDITIONAL GO с багами → АВТОМАТИЧЕСКИ переходи к Разработчику с баг-репортами, цикл повторяется**
12. **Если GO → АВТОМАТИЧЕСКИ переходи к Этапу 4 (DevOps)**

**Скилл:** `SKILL_TESTER.md`

### Цикл баг-фикса (автоматический):

```
Тестировщик: BUG-001 найден → 🔄 Разработчик: фикс → 🔄 Тестировщик: ретест
→ [если ещё баги] → 🔄 Разработчик: фикс → 🔄 Тестировщик: ретест
→ [если GO] → 🚀 DevOps
```

### Этап 4 — DevOps (АВТОМАТИЧЕСКИЙ, ПОЛНАЯ ПЕРЕСБОРКА):

1. Выведи: `🚀 DEVOPS: Начинаю полную пересборку и деплой`
2. **НЕ задавать вопросов пользователю.** Все параметры определяются автоматически:
   - Docker-compose файл: `docker-compose.dev.yml` (если есть), иначе `docker-compose.yml`
   - Миграции БД: проверить `git diff` на `prisma/schema.prisma`. Если есть изменения → выполнить `npx prisma db push`. Если нет → пропустить
3. **ПОЛНАЯ ПЕРЕСБОРКА ВСЕХ СЕРВИСОВ:**
   ```bash
   docker compose -f docker-compose.dev.yml build --no-cache
   docker compose -f docker-compose.dev.yml up -d --force-recreate
   ```
   **ЗАПРЕЩЕНО:** пересобирать только один сервис. **ВСЕГДА:** полная пересборка.
4. Дождись healthcheck ВСЕХ сервисов:
   ```bash
   docker compose -f docker-compose.dev.yml ps
   ```
   Все сервисы должны быть `healthy`. Таймаут 60 сек.
5. Проверь логи на отсутствие ошибок:
   ```bash
   docker compose -f docker-compose.dev.yml logs --tail=50
   ```
   Искать: `error`, `fatal`, `NOAUTH`, `ECONNREFUSED`, `panic`
6. **ПОЛНАЯ ПРОВЕРКА ДОСТУПНОСТИ:**
   ```bash
   curl -f http://localhost:3000/api/health
   ```
   Проверить что Redis подключение работает (в ответе healthcheck или через redis-cli ping)
7. Если всё прошло → выведи итог:
   ```
   ✅ Образ собран (все сервисы)
   ✅ Контейнеры запущены и healthy
   ✅ Redis OK
   ✅ PostgreSQL OK
   ✅ HTTP доступность OK (http://localhost:3000)
   🎉 Деплой завершён успешно
   ```
8. Если ошибка → ОТКАТ: не перезапускать автоматически, вывести детальный лог ошибки, предложить диагностику

**Скилл:** `SKILL_DEVOPS.md`

### Постдеплойный рестарт (ПРАВИЛО 7):

Если после успешного деплоя пользователь сообщает об ошибке **В ТЕЙ ЖЕ сессии**:
1. Выведи: `🔄 ОБНАРУЖЕНА ПРОБЛЕМА ПОСЛЕ ДЕПЛОЯ. Перезапуск конвейера.`
2. **АВТОМАТИЧЕСКИ перезапусти конвейер с Этапа 1 (Аналитик)**
3. Аналитик создаёт НОВОЕ ЧТЗ для исправления проблемы
4. Полный цикл: Аналитик → Разработчик → Тестировщик → DevOps
5. DevOps делает ПОЛНУЮ пересборку с исправлениями

**Триггеры (ключевые слова пользователя):**
«не работает», «ошибка», «баг», «сломалось», «вижу проблему», «после деплоя не работает»

## 10. Отдельный конвейер: Продакшн-деплой (PIPELINE_PROD.js)

> ⚠️ **СТАТУС: НЕ АКТИВЕН.** VPS и домен появятся позже.
> Все параметры прода собраны в `PROD_CONFIG` в начале `PIPELINE_PROD.js`.
> Когда появится VPS и домен — заполнить плейсхолдеры `<VPS_IP>`, `<DOMAIN>` — конвейер активируется автоматически.

### Когда активируется

**Триггерные фразы пользователя:**
«деплой на прод», «задеплой», «деплой в прод», «выложить на прод», «push to prod», «deploy to production», «запусти прод деплой»

**Если PROD_CONFIG ещё не заполнен:** сообщить пользователю, что прод не настроен (нет VPS/домена), предложить деплой через основной конвейер (PIPELINE.js, локально).

### Отличие от основного конвейера

| Аспект | Основной (PIPELINE.js) | Прод (PIPELINE_PROD.js) |
|--------|----------------------|------------------------|
| Среда | Локально (docker-compose.dev.yml) | VPS `<VPS_IP>` (docker-compose.yml) |
| Порт | 3000 | 3001 (prod), 3003 (green) |
| Стратегия | Пересборка всех контейнеров | Blue-Green (образ из GHCR) |
| Откат | Не требуется | Автоматический при провале |
| ЧТЗ | Обязателен | Не нужен (инфраструктурная операция) |
| Версионирование | Нет | Обязательное (semver + git tag) |
| Тестирование | Unit (Jest) | API автотесты + ручное E2E на проде |
| Скилл | SKILL_DEVOPS.md | SKILL_DEVOPS_PROD.md |

### Маршрут продакшн-деплоя

```
Пользователь: «деплой на прод»

🔍 PRE-FLIGHT:
  → проверка ветки (main)
  → проверка CI статуса
  → проверка VPS доступности
  → проверка диска и .env
  → фиксация текущего состояния

🏷️ VERSIONING:
  → анализ коммитов → patch / minor / major
  → npm version <type> --no-git-tag-version
  → обновление CHANGELOG.md
  → git commit + git tag v<version>

💾 BACKUP:
  → pg_dump (бэкап БД)
  → бэкап nginx конфига

🏗️ BUILD:
  → git push origin main (если не запушено)
  → ожидание CI completion
  → docker pull образа на VPS

🚀 DEPLOY (Blue-Green):
  → GREEN на порту 3003
  → healthcheck GREEN
  → nginx → GREEN
  → smoke tests
  → production на 3001
  → cleanup GREEN

✅ VERIFY:
  → контейнер healthy
  → HTTP /api/health → 200
  → Redis + PostgreSQL OK
  → SSL https://<DOMAIN> → 200
  → логи без ошибок

🧪 FULL TESTING:
  → автотесты API (health, HTTP статусы, функциональность, SSL, perf)
  → ручное E2E: главная, форма заявки, SEO, мобильная
  → вердикт: GO / CONDITIONAL GO / NO-GO

📋 FINALIZE:
  → cleanup старых образов
  → Telegram уведомление (с версией)
  → Deployment Report

👁️ WATCH (5 мин):
  → мониторинг healthcheck каждые 60 сек

При провале ЛЮБОГО критического шага → 🔄 АВТОМАТИЧЕСКИЙ ОТКАТ
```

## 11. Чеклист: как работает конвейер

### Маршрут 1: Стандартная задача

```
Пользователь: «Добавь в форму заявки поле "Тип мебели"»

📋 АНАЛИТИК:
  → изучает код
  → определяет маршрут: Разработчик (код/фича)
  → задаёт вопросы (question tool) — только если что-то неясно
  → пользователь отвечает (или дефолт)
  → создаёт ЧТЗ → требования/ЧТЗ_Поле_Тип_Мебели.md
  → 🔄 авто-переход

💻 РАЗРАБОТЧИК:
  → задаёт вопросы (question tool) — только если что-то неясно
  → пользователь отвечает (или дефолт)
  → пишет код + тесты
  → npm test && lint && tsc ✅
  → 🔄 авто-переход

🧪 ТЕСТИРОВЩИК:
  → создаёт тест-кейсы по ЧТЗ
  → запускает npm test && lint && tsc
  → ГЛУБОКАЯ ПРОВЕРКА: читает каждый изменённый файл, сверяет с ЧТЗ
  → проверяет edge cases, error handling, безопасность
  → найден BUG-001 → 🔄 авто-переход к Разработчику

💻 РАЗРАБОТЧИК (фикс):
  → фиксит BUG-001
  → npm test && lint && tsc ✅
  → 🔄 авто-переход к Тестировщику

🧪 ТЕСТИРОВЩИК (ретест):
  → BUG-001 ✅
  → GO → 🔄 авто-переход к DevOps

🚀 DEVOPS:
  → ПОЛНАЯ пересборка ВСЕХ сервисов (--no-cache + --force-recreate)
  → healthcheck всех сервисов
  → проверка логов на ошибки (error, NOAUTH, ECONNREFUSED)
  → проверка HTTP + Redis + PostgreSQL доступности
  → ✅ Деплой завершён

🎉 ГОТОВО.
```

## 12. Схема маршрутизации (визуальная)

```
Задача поступила
  │
  ├─ Сложная (архитектурная)? ──ДА──→ 🏗️ АРХИТЕКТОР
  │                                       │
  │                                       ↓
  │                                  ADR + проектные решения
  │                                       │
  │                                       ↓
  │                                  Вернулся к Аналитику
  │                                       │
  └─ НЕТ (или вернулся от Архитектора) ───┤
                                          │
                                    📋 АНАЛИТИК пишет ЧТЗ
                                          │
                                    ├─ Код/фича? ──→ 💻 РАЗРАБОТЧИК
                                    │                    │
                                    │                    ↓
                                    │               🧪 ТЕСТИРОВЩИК
                                    │                    │
                                    │                    ↓ (GO)
                                    │               🚀 DEVOPS (деплой)
                                    │
                                    └─ Инфраструктура? ──→ 🚀 DEVOPS (прямая задача)

                                    ┌──────────────────────────────────┐
                                    │ После деплоя: пользователь нашёл │
                                    │ ошибку → 🔄 РЕСТАРТ с Аналитика  │
                                    └──────────────────────────────────┘
```
